# Фаза 2 — Движок расчёта

Зависит от фазы 1 (`app/loaders`, `app/models.py`, `tests/fixtures/`).

## Цель

Из единой модели данных получить итоговый список рекомендованных заказов
с обоснованием. Закрывает требования R1–R6 (`.planning/REQUIREMENTS.md`).

## Модули

### `app/engine/segmentation.py`
Делит SKU на три сегмента по продажам за последние 12 месяцев
(`sales_monthly`):
- `regular` — продажи в ≥4 из последних 12 месяцев → идёт в forecast.
- `sparse` — продажи в 1–3 месяцах → правило min/max (страховой запас =
  максимум месячных продаж за последние 12 мес., заказ = max(0, min_level
  − свободный остаток), без сезонной модели.
- `dead` — 0 продаж за 12 месяцев → **не участвует в расчёте**, попадает
  в отдельный список `review_needed` (SKU, последняя дата продажи).

### `app/engine/cleaning.py` — R4
На `sales_tx` для каждого `sku_code`: медиана и MAD по величине строки
транзакции; строка — выброс, если робастный z-score
`(x - median) / (1.4826 * MAD)` > 10 **и** её доля в суммарном объёме
SKU за период > 20%. Выбросы исключаются из данных, идущих в forecast,
но не удаляются физически — помечаются полем `is_outlier`, чтобы решение
было объяснимо.

### `app/engine/stockout.py` — R3
На `stock_monthly` + `sales_monthly`: месяц SKU — stockout, если
`opening_stock <= 0` в этом месяце (используем то же условие, что дало
данные в `docs/validation.md`, а не абсолютный порог). Для таких месяцев
заменяем фактические продажи оценкой: медиана продаж SKU по не-stockout
месяцам того же календарного месяца (year-over-year), если есть история,
иначе медиана по всем не-stockout месяцам SKU.

### `app/engine/forecast.py` — R1, R2
Только для сегмента `regular`, на очищенных от выбросов и
скорректированных на stockout продажах:
1. Сезонный индекс по месяцу: `индекс(m) = среднее(qty за месяц m) /
   среднее(qty за все месяцы)`, если истории <12 мес. — индекс = 1
   (без сезонности).
2. Тренд роста: отношение продаж за последние 3 полных месяца к продажам
   за предыдущие 3 месяца, ограничить диапазоном [0.5, 2.0] (устойчивость
   к выбросам, п.9 RULE.md).
3. Базовый месячный прогноз = среднее за последние 12 мес. (после очистки)
   × сезонный индекс целевого месяца × тренд.

### `app/engine/order.py` — R1, R6
Итоговое количество на SKU:
```
период_покрытия_мес = (lead_time_days + coverage_days) / 30   # конфиг
потребность = прогноз_на_месяц × период_покрытия_мес + страховой_запас
             − свободный_остаток − in_transit
рекомендация = max(0, ceil(потребность / moq) × moq)
```
`lead_time_days` и `coverage_days` — параметры по поставщику в
`app/config.py`, с дефолтами (например, 30 и 30) и возможностью
переопределить из UI (фаза 3).

### `app/engine/explain.py` — R5
Для каждой строки — короткий текст из компонентов: сегмент, сезонный
индекс, тренд, факт stockout-корректировки, факт исключения выброса,
свободный остаток, в пути, MOQ. Пример: «Regular, сезонный пик ×1.4,
рост спроса +12%, скорректировано на stockout (2 мес.), остаток 5,
в пути 0, округлено до MOQ=6 → 18 шт.»

### `app/engine/pipeline.py`
`build_recommendations(data: dict, config) -> (orders_df, review_needed_df)`
— склеивает все модули в один вызов для UI и для тестов.

## Тесты (`tests/test_engine.py`)

По одному тесту на каждое требование R1–R6 из `.planning/REQUIREMENTS.md`,
на фикстурах `SEASONAL-1`, `STOCKOUT-1`, `OUTLIER-1` из фазы 1 (добавить
недостающие синтетические SKU для R1 и R6, если фаза 1 их не покрыла).

## Критерии приёмки

- `pytest tests/test_engine.py` зелёный, включая все R1–R6.
- Ни один модуль не содержит кода отправки (email/HTTP) — только расчёт.
- Обновить `.planning/STATE.md`.

# Фаза 3 — UI и экспорт

Зависит от фазы 2 (`app/engine/pipeline.py`).

## Цель

Streamlit-приложение поверх `build_recommendations()` + экспорт в xlsx,
совместимый по колонкам с 1С.

## Задача R — исправления движка по ревью фазы 2 (делать первой)

Найдено при проверке на реальных данных 2026-09-23. Каждое — с тестом.

1. **R4 не работает для редких SKU (ошибка).** `order.py` для `sparse`
   берёт `max_level` из сырых месячных продаж, без очистки от выбросов.
   Пример: `081100392_` — одна продажа 400 шт., очищенный максимум 2 шт.,
   рекомендация 399 шт. Таких SKU 14. Исправить: `max_level` для `sparse`
   считать по `monthly_clean` из `cleaning.py` (последние 12 полных мес.).
   Тест: sparse-SKU с одной аномальной накладной не заказывает её объём.
2. **Категории товаров не используются (пробел must have 1).** RULE.md
   п.7.1 требует учитывать категории, п.3 — «запускает расчёт по складу
   или категории». Категории есть только у SE: колонка «Категория 2026»
   в файле «Товар в пути» (значения 1, 2, 3, 5, 7). Сделать: загрузить в
   `sku_ref.category` (IEK и SKU без категории — «без категории»);
   колонка в выдаче и выгрузке; фильтр по категории в UI.
3. **«Прогноз по приросту» как вход (пробел must have 1).** Добавить в
   `EngineConfig` параметр `planned_growth` (по поставщику, по умолчанию
   0%) — множитель `(1 + planned_growth)` к прогнозу `F(m)`, поле в UI,
   упоминание в обосновании, если ≠ 0. Тест: +10% → потребность растёт.
4. **Новые SKU недооцениваются.** 51 регулярный SKU начал продаваться
   внутри 12-месячного окна; уровень `L` сейчас — среднее по 12 мес.
   вместе с нулями до старта продаж. Считать `L` только по месяцам,
   начиная с первой продажи SKU (но не меньше 4 мес.).
5. **Ограничение 2024 года пропущено для 213 SKU.** `cleaning.py` считает
   начало транзакций по SKU; у 213 SKU есть единичные строки 2023–2024,
   и для них 2024 год не ограничивается сверху. Брать общее начало
   покрытия транзакций: первый месяц, где строк по поставщику ≥ 1000
   (фактически 2025-01).
6. **Остаток IEK неизвестен у 100 SKU — и они в топе списка.** Текущий
   остаток IEK = начало сентября − продажи сентября. У 100 SKU продажи
   сентября больше остатка на начало — значит, были приходы, и настоящий
   остаток неизвестен, а не 0. Сейчас они получают «остаток 0», завышенный
   заказ и первые места (пример: `130300792_`, 26 700 шт.). Сделать: флаг
   `stock_unknown`, если продажи месяца > остатка на начало; срочность —
   «проверить остаток», в обосновании — «в сентябре были приходы, остаток
   в данных неизвестен — сверьте с 1С перед заказом»; в UI такие строки
   выделить и не ставить в начало сортировки. Количество не менять.

## Задачи

0. **Кэширование обязательно.** `load_all()` на реальных данных занимает
   ~21 с. Обернуть загрузку в `st.cache_data` (и расчёт — по параметрам),
   иначе каждое изменение виджета ждёт 21 с и демо не работает.
1. `app/ui/streamlit_app.py`:
   - выбор поставщика (IEK / SE / оба) и **категории (обязательно, см.
     задачу R.2)**, поиск по SKU;
   - поле «плановый прирост, %» по поставщику (задача R.3);
   - поля для `lead_time_days` / `coverage_days` (дефолты из конфига,
     редактируемые);
   - кнопка «Рассчитать» → таблица рекомендаций, сгруппированная по
     поставщику, с колонками: Код 1С, Артикул, Наименование, Поставщик,
     Рекомендуемое количество, Срочность, Обоснование;
   - отдельный блок/вкладка «На проверку» — SKU без продаж за 12 мес.
     (`review_needed` из фазы 2);
   - кнопка экспорта в xlsx (`app/export.py`, `pandas.to_excel` +
     `openpyxl`): **отдельный лист на каждого поставщика** с колонками
     Код 1С, Артикул поставщика, Наименование, Ед., Количество — заголовок
     в первой строке, без объединённых ячеек и пустых строк сверху
     (под загрузку «Заказа поставщику» в 1С:УТ); плюс лист «Обоснование»
     со всеми строками, поставщиком, срочностью и текстом;
   - показывать дату среза данных (`AS_OF`) и значения сроков поставки
     с пометкой источника (IEK — из данных, SE — допущение);
   - **никакой отправки заказа поставщику** — только просмотр и экспорт
     локального файла (RULE.md п.9).
2. Срочность уже считается в фазе 2 (`order.py`) — здесь только
   отображение и сортировка (высокая сверху).
3. `app/main.py` или `run.sh`/инструкция в README — как запустить
   (`streamlit run app/ui/streamlit_app.py`).

## Критерии приёмки

- `streamlit run app/ui/streamlit_app.py` запускается без ошибок на
  реальных данных из `data/raw/`; повторный расчёт после смены параметра
  занимает секунды, а не ~21 с.
- Тест на `app/export.py`: в файле есть лист на каждого поставщика с
  нужными колонками в первой строке и лист «Обоснование».
- Экспортированный xlsx открывается и содержит все обязательные колонки
  из `.planning/REQUIREMENTS.md`.
- Обновить `.planning/STATE.md`.

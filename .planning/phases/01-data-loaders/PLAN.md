# Фаза 1 — Загрузчики и единая модель данных

## Цель

Прочитать xlsx-файлы обоих поставщиков и привести их к одной внутренней
модели, на которой будут работать все дальнейшие фазы. Плюс синтетический
тестовый набор, на котором проверяются все требования R1–R6.

## Входные файлы (реальные, только для ручной проверки — не в тестах)

`data/raw/IEK/*.xlsx`, `data/raw/Systeme electric/*.xlsx` (человек копирует
файлы из корня репозитория в `data/raw/` перед первым запуском; `data/raw/`
в `.gitignore`).

Структура каждого файла и особенности — см. `.planning/PROJECT.md` и
таблицу ниже. При открытии реальных файлов расхождения с этим описанием
возможны — в этом случае адаптируй загрузчик и сообщи об этом в отчёте,
план не переписывай без необходимости.

| Файл | Ключевое | Особенности |
|---|---|---|
| Динамика продаж (транзакции) | Дата, Номер, Документ, Код, Номенклатура, Ед., Склад, Количество | фильтровать `Документ` по `Расходная накладная`; количество отрицательное — брать `abs()` |
| Ежемесячные продажи | Номенклатура, Код, [IEK: 2 строки заголовка / SE: Артикул+Кратность, 2 строки заголовка], далее месяцы 01.2024–09.2026, Итого | wide-формат, парсить месяц из заголовка |
| Ежемесячные остатки | Номенклатура, Ед., Код, 3 строки заголовка (Количество / нач.остаток), далее месяцы | нач. остаток на начало месяца |
| Товар в пути | IEK: колонки-документы поставки, значения — количество; SE: колонка «СЭ в пути» + готовые Кэф. роста/сез-ти/Запас (справочно, не использовать в движке фазы 2 — это Excel-методика партнёра для сверки на этапе ревью) | |
| MOQ | IEK: «Мин. разр. к отгр.»; SE: «Кратность» | если MOQ отсутствует для SKU — считать 1 |

## Единая модель (общая для обоих поставщиков)

```python
# app/models.py
sales_tx:      DataFrame[date, sku_code, supplier, qty]
sales_monthly: DataFrame[sku_code, supplier, month(YYYY-MM), qty]
stock_monthly: DataFrame[sku_code, supplier, month(YYYY-MM), opening_stock]
in_transit:    DataFrame[sku_code, supplier, qty]           # текущий суммарный объём в пути
moq:           DataFrame[sku_code, supplier, moq]
sku_ref:       DataFrame[sku_code, supplier, name]
```

`supplier` ∈ {`IEK`, `SE`}. `sku_code` — значение колонки «Код 1с» /
«Номенклатура.Код», используется как единственный ключ связывания таблиц.

## Задачи

1. `app/loaders/iek.py`, `app/loaders/se.py` — функции
   `load_<table>(path) -> DataFrame` по каждой таблице модели.
2. `app/loaders/__init__.py` — `load_all(data_dir) -> dict[str, DataFrame]`,
   объединяющий оба поставщика в единые `sales_tx`, `sales_monthly` и т.д.
3. `tests/fixtures/` — 2–3 маленьких xlsx или CSV-фикстуры (не реальные
   данные партнёра), синтетические, с тремя специально сконструированными
   SKU:
   - `SEASONAL-1` — выраженный сезонный пик (для R2 в фазе 2),
   - `STOCKOUT-1` — 2 месяца нулевого остатка и просевшие продажи в них
     (для R3),
   - `OUTLIER-1` — стабильный спрос + одна аномальная накладная (для R4).
4. `tests/test_loaders.py` — загрузчики читают фикстуры и возвращают
   DataFrame с ожидаемыми колонками и типами; строки с
   `Приходная накладная` / `Заказ покупателя` в транзакциях отфильтрованы.

## Критерии приёмки

- `pytest tests/test_loaders.py` зелёный.
- `load_all()` на реальных файлах в `data/raw/` (ручной прогон, не в CI)
  отрабатывает без исключений и даёт непустые DataFrame по каждому ключу.
- Обновить `.planning/STATE.md`: статус фазы 1.

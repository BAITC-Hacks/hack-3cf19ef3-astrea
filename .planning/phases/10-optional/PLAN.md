## 10B. Приоритизация по риску дефицита (п.8, пункт 1)

- В `app/engine/order.py` (без изменения количества заказа) добавить поля:
  - `days_of_cover = (free_stock + in_transit) / дневной прогноз` (∞ при нулевом прогнозе);
  - `stockout_date = AS_OF + days_of_cover` (если < AS_OF + горизонт);
  - `risk_score` 0–100: 100 — покрытия нет совсем; падает линейно до 0 при
    покрытии ≥ `lead_time + coverage`; для `stock_unknown` — отдельный признак,
    не число.
- Срочность выводится из `risk_score` (те же 3 уровня, пороги как сейчас:
  `< lead_time` → Срочно, `< lead_time + coverage` → Скоро, иначе Позже) —
  **поведение и тесты срочности не меняются**.
- В таблице: колонка «Хватит на» (`N дн.` или `—`), сортировка по `risk_score`.
  В панели «Почему N шт.» — строка «Закончится ~ДД.ММ, поставка придёт через
  L дн.».
- Тесты: `days_of_cover` и `risk_score` на синтетике (нулевой остаток → 100,
  большой остаток → 0, монотонность); срочность прежняя.

  CREATE TABLE IF NOT EXISTS supplier_terms (
      supplier        TEXT PRIMARY KEY CHECK (supplier IN ('IEK', 'SE')),
      lead_time_days  INTEGER NOT NULL CHECK (lead_time_days > 0),
      order_cycle_days INTEGER NOT NULL CHECK (order_cycle_days > 0),  -- = период покрытия

## 10E. Выгрузка и отправка заказа поставщику (п.8, пункт 4) — только после подтверждения

RULE.md п.9: **нельзя** отправлять без подтверждения ответственного сотрудника.

- Отправка возможна **только для утверждённого заказа** (страница «История
  заказов» и сообщение после утверждения): кнопка «Отправить поставщику» →
  **диалог предпросмотра** (`st.dialog`): кому (`supplier_terms.contact_email`,
  можно исправить), тема, короткий текст, вложение `astrea_<поставщик>_<№>.xlsx`
  → кнопка «Подтвердить отправку». Никаких автоматических отправок, таймеров,
  фоновых задач.
- **Сервис — Resend** (решение человека 2026-09-23 по рекомендации Claude;
  бесплатно 3 000 писем/мес, 100/день; вложения до 40 МБ):
  `POST https://api.resend.com/emails`, заголовок
  `Authorization: Bearer $RESEND_API_KEY`, тело — `from`, `to`, `subject`,
  `text`, `reply_to`, `attachments: [{filename, content(base64)}]`.
  Вызов — `urllib.request` (без SDK и новых зависимостей), таймаут 15 с,
  ошибка API → статус `failed` с текстом ответа в журнале.
- **Отправитель:** `ORDERS_FROM` (по умолчанию `Astrea <orders@astrea.one>`);
  домен `astrea.one` подтверждается в Resend DNS-записями в Spaceship
  (делает человек). **Reply-To — email пользователя, утвердившего заказ**
  (у `astrea.one` нет почтового ящика).
- **Адреса поставщиков по умолчанию пустые** (`supplier_terms.contact_email`):
  во время хакатона нельзя случайно написать настоящим IEK/Systeme Electric.
  Получатель виден и редактируется в предпросмотре.
- Если `RESEND_API_KEY` не задан — кнопка «Скачать письмо (.eml)» вместо
  отправки (формирование — `email.message.EmailMessage`), пометка «Отправка
  не настроена». Ключ — только в серверном `.env`.
- Журнал — миграция `005_order_dispatches.sql`: `order_id`, `sent_by`,
  `sent_at`, `recipient`, `status` (`sent`/`failed`/`eml`), `error`.
  В «Истории заказов» — статус отправки у заказа. Повторная отправка — только
  снова через предпросмотр и подтверждение.
- `.env.example`: `RESEND_API_KEY=` и `ORDERS_FROM=` пустые, с комментарием.
  Ключи в код и `.env.example` не писать.
- Тесты: без подтверждения отправки нет; неутверждённый заказ отправить нельзя;
  при заданном `RESEND_API_KEY` выполняется запрос к Resend (`urllib`
  подменён в тесте) с верным `to`, `reply_to` и base64-вложением; без ключа
  формируется `.eml`; запись в журнал. **В тестах реальные письма не
  отправляются.**

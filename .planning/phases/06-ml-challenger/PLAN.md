# Фаза 6 — ML-модель-соперник, обученная на реальных данных

Решение человека 2026-09-23: добавить обучаемую модель прогноза и честно
сравнить её с формулой и методикой партнёра. **Порядок:** после фазы 3
(включая задачу R), до README (фаза 4) и деплоя (фаза 5).

Новая зависимость **`scikit-learn==1.6.1`** одобрена человеком (поддерживает
Python 3.9 локально и 3.12 в Docker). Других зависимостей не добавлять.
GPU не нужен: модель учится на CPU за секунды.

## Идея

Одна **глобальная** модель на все регулярные SKU обоих поставщиков
(`HistGradientBoostingRegressor`). У каждого SKU всего ~32 месяца
истории, это мало для отдельной модели на SKU, а общая модель учится на
закономерностях всего ассортимента. Модель — **соперник** формулы: в
продукт она попадает по заранее заданному правилу (ниже), только если
точнее на отложенных данных.

## Данные для обучения

Источник — ряд `demand` из `prepare_forecasts()`
(`app/engine/pipeline.py`): продажи, очищенные от разовых заказов и
восстановленные в месяцы дефицита. То есть модель учится на тех же
очищенных данных, что и формула. Только сегмент `regular`.

**Пример для обучения** = (SKU, месяц-точка отсчёта t, горизонт h),
h = 1…6. Цель — `demand(t + h)`. Признаки считаются **только по данным
≤ t**.

**Масштаб:** все признаки со спросом и цель делятся на
`base = mean(demand за 12 мес. до t включительно) + 1`, модель
предсказывает отношение, ответ умножается обратно на `base`. Так SKU с
продажами 5 и 5000 шт./мес. обучаются вместе.

**Признаки** (все по данным ≤ t, со спросом — в долях `base`):
- лаги: `demand(t)`, `t−1`, `t−2`, `t−5`, `t−11`;
- скользящие средние за 3 и 6 месяцев;
- тот же месяц год назад: `demand(t + h − 12)`;
- сезонные индексы месяца `t + h`: SKU и поставщика (`seasonal_indices`,
  `supplier_seasonal_indices` из `app/engine/forecast.py`, посчитанные по
  данным ≤ t);
- рост год к году `g` (как в формуле), доля месяцев без продаж за 12 мес.,
  число месяцев дефицита за 12 мес.;
- номер месяца `t + h`, горизонт `h`, поставщик (IEK/SE), категория
  (из `sku_ref.category`, «без категории» → отдельное значение).

**Точки отсчёта:** от 2024-12 (нужно 12 мес. истории) до `train_end − h`,
чтобы цель ≤ `train_end`.

## Модель (гиперпараметры фиксируются заранее, не подбираются на тесте)

```python
HistGradientBoostingRegressor(
    loss="absolute_error",      # совпадает с WAPE
    learning_rate=0.05, max_iter=300, max_leaf_nodes=31,
    min_samples_leaf=50, l2_regularization=1.0,
    categorical_features=[<индексы supplier, category, target_month>],
    random_state=0,
)
```

## Модули

- `app/engine/ml.py`:
  - `build_training_frame(demand, segments, sku_ref, train_end, horizons=range(1, 7))`
    → признаки + цель;
  - `build_prediction_frame(demand, segments, sku_ref, origin, horizons)` → признаки для прогноза;
  - `train_model(frame)`;
  - `predict(model, frame)` → `[sku_code, supplier, month, ml_forecast]`;
  - `feature_importance(model, frame)` → permutation importance (топ-10), для README и интерфейса.
- `EngineConfig.forecast_method: Literal["formula", "ml"]`. В `order.py`
  прогноз `F(m)` берётся из выбранного метода. Плановый прирост, страховой
  запас, остатки и MOQ считаются как раньше. Если окно выходит за h = 6,
  для месяцев сверх этого берётся формула; в обосновании это указывается.
- **Обоснование (объяснимость, RULE.md п.9)** при методе `ml` содержит оба
  прогноза: «ML-прогноз N шт./мес.; формула M шт./мес. (уровень, рост,
  сезонность …)», дальше как сейчас. Разложение формулы остаётся, чтобы
  цифру можно было проверить.
- `app/ui/streamlit_app.py`:
  - переключатель «Метод прогноза: формула / ML», по умолчанию — метод, выбранный правилом ниже;
  - модель обучается один раз и кэшируется (`st.cache_resource`) по данным ≤ последнего полного месяца;
  - блок «Что влияет на ML-прогноз» с топ-10 признаков.
- `scripts/backtest.py`: третий метод «ML», обученный на `train_end = 2026-06`,
  прогноз на 2026-07 (h = 1) и 2026-08 (h = 2). Те же SKU, те же метрики:
  WAPE, MdAPE по IEK и SE. Вся подготовка (очистка, дефициты, сезонность)
  — по данным ≤ 2026-06, как у формулы.

## Правило выбора метода (задано до получения результатов)

Точка отсчёта — формула после задачи R: **WAPE IEK 39,11%, SE 25,25%;
MdAPE IEK 58,08%, SE 48,90%**.

- ML становится методом по умолчанию для поставщика, если на бэктесте
  **WAPE ниже формулы минимум на 5% относительно** (например, для IEK
  ≤ 37,15%) **и MdAPE не хуже**.
- Иначе по умолчанию остаётся формула, а ML доступен переключателем. В
  README пишем результат как есть.
- **Гиперпараметры и признаки не менять после того, как увидели цифры
  июля–августа.** Если очень хочется что-то поменять, сначала опиши это в
  отчёте и получи согласие человека. Иначе бэктест перестаёт быть честным.

## Тесты (`tests/test_ml.py`)

1. **Нет утечки из будущего:** изменение `demand` в месяцах > t не меняет
   признаки для точки отсчёта t.
2. Обучающая таблица: у всех строк цель ≤ `train_end`; нет NaN в признаках.
3. Модель обучается и даёт конечные неотрицательные прогнозы на фикстурах.
4. `build_recommendations(config.forecast_method="ml")` отрабатывает на
   фикстурах, у каждой строки есть обоснование с обоими прогнозами.
5. Существующие тесты R1–R6 не меняются и проходят (они проверяют метод
   `formula`).

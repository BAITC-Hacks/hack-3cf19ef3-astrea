# Проект: автоматический расчёт заказов поставщикам

Источник: RULE.md (кейс партнёра ТОО «Электрокомплект», хакатон HACKALEM AI).
Обоснование и вердикт GO — `docs/validation.md`.

## Цель

Менеджер отдела закупа запускает расчёт по складу/поставщику и получает
список рекомендованных заказов с обоснованием по каждой позиции — вместо
ручного пересчёта в Excel.

## Пользователь и сценарий

Менеджер отдела закупа → выбирает поставщика (IEK или Systeme Electric),
опционально категорию → получает таблицу рекомендаций (артикул, поставщик,
количество, срочность, обоснование), сгруппированную по поставщикам →
проверяет, экспортирует в xlsx.

## Данные (только чтение, лежат в `data/raw/`, **коммитятся в репозиторий**)

- `IEK/*.xlsx`, `Systeme electric/*.xlsx` — транзакции продаж, помесячные
  продажи, помесячные остатки, товар в пути, MOQ/кратность, сезонность.
  Формат отличается между поставщиками — два отдельных загрузчика.
- Решение человека (2026-09-23): данные партнёра коммитятся, чтобы жюри
  могло запустить решение на реальных данных. Данных о клиентах в них нет.
  Объём ~16 МБ.
- Дата среза данных: **2026-09-22** (последняя транзакция). Сентябрь 2026 —
  неполный месяц.

## Жёсткие ограничения (RULE.md п.9, обязательны к соблюдению в коде)

- Никогда не отправлять заказ поставщику автоматически — только показать
  человеку для подтверждения. Ни один код не должен вызывать email/HTTP
  отправку заказа.
- Не использовать неанонимизированные данные о клиентах. ID клиента в
  источниках отсутствует — ничего дополнительно анонимизировать не нужно,
  но не добавлять новых полей с клиентскими данными.
- Каждая рекомендация должна сопровождаться текстовым обоснованием
  (объяснимость расчёта).
- Алгоритм должен быть устойчив к выбросам/аномалиям во входных данных
  (см. must-have 4).
- Выходной формат должен быть совместим с 1С: колонки Код 1С, Артикул,
  Наименование, Количество.

## Ограничения проекта (не путать с ограничениями кейса)

- Дедлайн < 1 суток → делаем только must-have (RULE.md п.7) + MOQ.
  Опциональные пункты (RULE.md п.8) не делаем.
- Стек: Python + Streamlit, зависимости только pandas, numpy, openpyxl,
  streamlit, pytest, **scikit-learn** (одобрен человеком 2026-09-23 для
  ML-модели-соперника, фаза 6) — requirements.txt.
- Сегментация спроса обязательна (см. `docs/validation.md` §6): частые
  SKU — через модель; редкие — через min/max по страховому запасу;
  SKU без продаж за 12 мес. — не заказываются, помечаются для ручной
  проверки.
- Сроки поставки — параметр `lead_time_days` на поставщика в конфиге,
  редактируется в UI. Значения по умолчанию:
  - **IEK — 24 дня.** Взято из данных: заголовки документов в файле
    «Путь ИЭК» содержат дату заказа и дату поступления (12 дней — 43%
    объёма, 24 дня — 54%, 35–40 дней — 3%); 24 дня — медиана по объёму.
  - **SE — 35 дней.** Допущение: в данных дат нет; Systeme Electric —
    российский производитель, аналог — российские поставки IEK (35–40 дней).
- Период покрытия `coverage_days` — 30 дней (допущение: заказ раз в месяц).
- Методика партнёра восстановлена из формул в SE-файле «Товар в пути»:
  прогноз = `Ср мес за 12 мес × (1 + Кэф. роста) × (1 + Кэф. сез-ти)`,
  где рост — те же 3 месяца год к году, сезонность — следующие 3 месяца
  к текущим 3 месяцам год назад. Это базовая модель для сравнения (Q1).

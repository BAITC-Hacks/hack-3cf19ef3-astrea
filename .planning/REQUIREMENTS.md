# Требования и критерии приёмки

Источник формулировок — RULE.md п.7 (must have) и п.9 (ограничения).
Каждый пункт закрывается минимум одним тестом pytest на синтетических
фикстурах (`tests/fixtures/`), не на реальных файлах партнёра.

## R1 — Базовая потребность по всем источникам данных

Расчёт учитывает историю продаж, текущие остатки, товар в пути,
категории товаров, прогноз по приросту. Изменение любого источника
(например, объёма товара в пути) отражается на итоговом количестве.

**Тест:** для фиксированного SKU посчитать рекомендацию дважды — с разным
объёмом «товар в пути» — итоговое количество должно отличаться
предсказуемым образом (растёт при уменьшении объёма в пути).

## R2 — Сезонность и устойчивый рост спроса

Для SKU с выраженной сезонностью прогноз отражает сезонный паттерн,
а не среднее по всей истории.

**Тест:** синтетический SKU с пиком продаж в фиксированные месяцы —
прогноз на пиковый месяц выше, чем прогноз на основе простого среднего
за 12 месяцев, минимум в 1.3 раза.

## R3 — Компенсация упущенного спроса (stockout)

Для SKU с периодом остатка ≈0 расчётная потребность скорректирована
в большую сторону по сравнению с расчётом по «сырым» фактическим
продажам.

**Тест:** синтетический SKU с 2 месяцами нулевого остатка и просевшими
продажами в эти месяцы — восстановленный спрос выше сырых продаж за
эти месяцы минимум на 20%.

## R4 — Исключение разовых крупных заказов

Искусственно добавленный в тестовые данные разовый крупный заказ
(включая крупную продажу одному клиенту/одной накладной) не приводит
к существенному росту рекомендуемого регулярного количества.

**Тест:** синтетический SKU со стабильным спросом + одна аномальная
накладная (>10x медианы) — рекомендация с аномалией и без неё
отличается не более чем на 10%.

## R5 — Итоговый список по поставщикам с обоснованием

Каждая строка выходного списка сопровождается текстовым обоснованием
и список можно посмотреть в разбивке по каждому поставщику.

**Тест:** для сгенерированного набора рекомендаций каждая строка имеет
непустое поле `explanation`; группировка по `supplier` не теряет строк
(sum по группам == общее количество строк).

## R6 — MOQ / кратность

Итоговое рекомендуемое количество кратно MOQ поставщика (округление
вверх), если MOQ для SKU известен.

**Тест:** при MOQ=6 и расчётной потребности 14 рекомендация — 18 (не 14
и не 12).

## Q1 — Проверка на истории против методики партнёра (условие GO)

Не must have кейса, но условие GO из `docs/validation.md` §6. Без неё на
демо и в README нельзя утверждать, что расчёт точнее.

**Проверка:** скрипт `scripts/backtest.py` на реальных данных: данные до
2026-06 включительно → прогноз на 2026-07 и 2026-08 → сравнение с фактом.
SKU — только те, у кого продажи в ≥9 из 12 месяцев (2025-07…2026-06).
Метрика — WAPE = Σ|факт − прогноз| / Σ факт, отдельно по IEK и SE.
Сравниваем с методикой партнёра (формула в `.planning/PROJECT.md`),
посчитанной на тех же данных. Результат (обе цифры, без подгонки)
записывается в README. Юнит-тест — только на функцию WAPE.

**Находка (2026-09-23, при ревью):** у методики партнёра WAPE по IEK
получается ~1198% — это не опечатка и не наш баг, а реальное свойство
формулы: коэффициент роста и коэффициент сезонности делятся на один и
тот же квартал год назад, и если в этом квартале у SKU был провал
продаж, оба коэффициента взрываются и перемножаются. На 818 SKU IEK
10 SKU с этим эффектом дают 94% суммарной ошибки. **Публиковать сырой
WAPE без пояснения нельзя** — читатель решит, что ошиблись мы. Поэтому
в `scripts/backtest.py` добавляется:
- медианная абсолютная процентная ошибка по SKU (MdAPE) — устойчива к
  выбросам, считается для обоих методов рядом с WAPE;
- диагностика: число SKU, где `partner_forecast > 10 × Ср_мес_12`,
  и их доля в суммарной ошибке.
В README (фаза 4) — обе метрики и короткое объяснение находки как
демонстрация нестабильности ручного Excel-метода на просевших
кварталах (это довод в пользу проекта, не в его ущерб).

## Ограничения (не функциональные требования, но проверяются)

- Нет кода, отправляющего заказ поставщику (grep по кодовой базе на
  отправку email/HTTP при экспорте — вручную на этапе ревью).
- Сегментация: SKU без продаж за последние 12 мес. не попадают в список
  рекомендаций по модели, попадают в отдельный список "на проверку".
- Экспорт xlsx: отдельный лист на каждого поставщика с колонками для
  загрузки в 1С — Код 1С, Артикул поставщика, Наименование, Ед.,
  Количество (заголовок в первой строке, без объединённых ячеек); плюс
  лист «Обоснование» — все строки с поставщиком, срочностью и текстом
  обоснования.

## Вне объёма (сознательно не делаем)

Приоритизация по риску дефицита, визуализация трендов, автоэкспорт/
рассылка поставщику — RULE.md п.8, опционально, за рамками дедлайна.

# Проверка идеи: автоматический расчёт заказов поставщикам

Дата: 2026-09-23 · Режим: ProofPilot, быстрая оценка (coach · validate) · Контекст: хакатон HACKALEM AI, кейс ТОО «Электрокомплект», до сдачи меньше суток.

## 1. Идея в одной фразе

**Клиент:** менеджер отдела закупа дистрибьютора электротехники (склад Алматы; поставщики IEK и Systeme Electric).
**Задача:** решить, сколько и чего заказать у каждого поставщика, чтобы не было ни дефицита, ни затоваривания.
**Обещанный результат:** за один запуск получить список заказов по поставщикам с количеством, срочностью и объяснением по каждой позиции. Сейчас это ручной расчёт в Excel.

## 2. Что известно, а что нет

| Утверждение | Статус |
|---|---|
| Расчёт делается вручную в Excel, редко, это приводит к излишкам и дефициту | заявление партнёра (RULE.md), независимо не проверено |
| У партнёра уже есть Excel-методика: средние продажи за 12 мес., коэффициенты роста и сезонности, запас | **факт**: колонки «Кэф. Роста», «Кэф. Сез-ти», «Запас», «Заказ» в `Товар в пути_SystemElectric` |
| Stockout — реальная проблема | **факт (данные)**: у IEK 533 активных SKU имели хотя бы один месяц с нулевым остатком на начало за последние 12 мес. (всего 2190 SKU-месяцев); у SE таких 31 SKU (195 SKU-месяцев) |
| Разовые крупные продажи искажают картину | **факт (данные)**: у 154 из 1240 SKU IEK и у 35 из 398 SKU SE (считались SKU с ≥10 строками продаж) одна строка накладной даёт >20% объёма и имеет робастный z > 10 |
| В данных есть ID клиента | **нет**. В транзакциях только номер накладной, поэтому «крупная продажа одному клиенту» определяется по накладной |
| Известны сроки поставки | **нет**, в данных их нет |
| Экономический эффект (стоимость излишков и упущенных продаж) | **неизвестно**, базовых цифр нет |

Внешние источники (рынок, конкуренты) **не проверялись**. Для хакатона это не нужно: заказчик и проблема заданы партнёром. Рыночных утверждений в этом документе нет.

## 3. Альтернативы

1. **Ничего не менять** — текущая Excel-методика партнёра. С ней мы и соревнуемся: наша ценность в автоматизации, учёте stockout, исключении выбросов и объяснимости, а не в «прогнозе вообще».
2. **Модули планирования закупок в учётной системе (1С) и специализированные сервисы прогнозирования.** Существуют как класс, но конкретные продукты не проверялись. Почему партнёр ими не пользуется — неизвестно, стоит спросить у ментора.

## 4. Рискованные допущения (по убыванию опасности)

1. **Разреженный спрос.** У IEK из 2463 SKU 537 не продавались ни разу за последние 12 мес., ещё 599 продавались только в 1–3 месяцах, то есть ~46% ассортимента редкие или «мёртвые». У SE таких ~30% (164 из 554). Сезонно-трендовая модель на таких позициях даст мусор. Без сегментации (частые / редкие / мёртвые) и отдельной логики для редких позиций результат будет выглядеть недостоверно для жюри и для закупщика.
2. **Качество прогноза не хуже текущей методики.** Если наш расчёт хуже Excel партнёра, ценность сводится к автоматизации. Проверяется бэктестом.
3. **Номер накладной — достаточный заменитель ID клиента** для поиска разовых крупных заказов. Правдоподобно, но не подтверждено.
4. **Сроки поставки.** Без них размер заказа — условность. Нужен параметр по поставщику и, в идеале, реальные значения от партнёра.
5. **Совместимость выгрузки с 1С.** Формат импорта неизвестен, допускаем xlsx с колонками Код 1С / Артикул / Кол-во.
6. **Время и форматы.** У двух поставщиков разные файлы (разные заголовки, колонки, MOQ есть не для всех SKU: у IEK для 1761 из 2463). Загрузка данных может съесть треть времени.

## 6. Вердикт

**Рекомендация: `go`** — строить MVP с ограничениями ниже. **Уверенность: средняя** в реализуемости, **низкая** в оценке экономического эффекта (нет базовых цифр).

Почему `go`: данные есть и хорошо стыкуются по коду 1С (у SE продажи, остатки и MOQ покрывают все 554 SKU, у IEK продажи и остатки совпадают по 2456 SKU из 2463). Все проблемы из must have видны в реальных данных. Заказчик уже определён. Для суток задача реалистична, если держать объём узким.

Условия `go` (без них я бы советовал `pivot` к «надстройке над Excel-методикой партнёра»):
- **Сегментация спроса обязательна**: частые SKU идут через модель; редкие через правило min/max по страховому запасу; «мёртвые» не заказываются и помечаются для ручной проверки.
- **Бэктест T1 показывается в README и на демо.** Без него утверждение «точнее» не делаем.
- **Из объёма убрано:** визуализация трендов, рассылка поставщикам, любая автоотправка (запрещена RULE.md п.9).
- **Условие остановки:** если через ~6 часов нет загрузки обоих поставщиков в единую модель, дальше делаем только IEK.

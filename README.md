## 1. Название проекта

**Автозаказ** — сервис автоматического расчёта рекомендованных заказов поставщикам для пополнения склада.

## 2. Краткое описание

**Проблема.** Менеджер отдела закупа «Электрокомплекта» считает, сколько товара дозаказать у поставщиков, вручную в Excel. Это трудоёмко, поэтому расчёт делают редко и не в реальном времени. В итоге по одним позициям склад затоварен, по другим возникает дефицит. Разовые крупные продажи одному клиенту искажают оценку регулярного спроса (постановка задачи — [RULE.md](RULE.md)).

**Для кого.** Для менеджера отдела закупа. Он запускает расчёт по поставщику и получает список позиций с рекомендуемым количеством и объяснением каждой цифры, затем проверяет и утверждает заказ сам.

## 3. Что реализовано

| Возможность | Статус |
|---|---|
| Загрузка xlsx-выгрузок из 1С по двум поставщикам (IEK, Systeme Electric) с разными форматами файлов | ✅ готово |
| Приведение к единой модели: продажи по накладным, продажи и остатки по месяцам, товар в пути, кратность (MOQ), справочник SKU | ✅ готово |
| Фильтрация служебных документов (приходные накладные, заказы покупателей) и нормализация знаков количества | ✅ готово |
| MOQ = 1 для SKU, у которых кратность не указана | ✅ готово |
| Тесты загрузчиков на синтетических данных | ✅ готово (6 тестов) |
| Движок расчёта: сегментация спроса, исключение разовых крупных заказов, восстановление спроса в периоды дефицита, сезонность и рост, округление до MOQ, текстовое обоснование | ⏳ в работе (фаза 2) |
| Проверка на истории: сравнение точности с текущей Excel-методикой партнёра | ⏳ в работе (фаза 2) |

## 4. Как работает решение

Целевой сценарий. Реализован первый шаг, остальные в работе:

1. **Входные данные** — выгрузки из 1С в `data/raw/`: продажи, остатки, товар в пути, кратность. ✅
2. **Загрузка** — `load_all()` читает файлы обоих поставщиков и приводит их к единой модели. ✅
3. **Расчёт** — по каждому SKU очищенный от выбросов прогноз спроса на срок поставки плюс период покрытия, минус остаток и товар в пути, с округлением до кратности. ⏳
4. **Результат** — таблица рекомендаций по поставщикам с обоснованием и срочностью, выгрузка в xlsx. Менеджер проверяет и утверждает сам, автоматической отправки поставщику нет. ⏳

## 5. Технологии

- **Язык:** Python 3.9+
- **Библиотеки** (версии зафиксированы в [requirements.txt](requirements.txt)): `pandas`, `numpy`, `openpyxl` (чтение xlsx), `streamlit` (интерфейс, фаза 3), `pytest` (тесты)
- **AI-модели, внешние API и сервисы:** не используются. Расчёт выполняется локально на выгрузках партнёра.

## 6. Архитектура проекта

```
data/raw/                      выгрузки 1С от партнёра (xlsx)
  ├─ IEK/
  └─ Systeme electric/
        │
        ▼
app/loaders/                   ✅ загрузка и нормализация
  ├─ iek.py                    адаптер форматов IEK
  ├─ se.py                     адаптер форматов Systeme Electric
  ├─ _shared.py                общий разбор: поиск заголовков, месяцы, «широкие» таблицы → «длинные»
  └─ __init__.py               load_all(): оба поставщика → единая модель
        │
        ▼
app/models.py                  ✅ схема единой модели и её проверка (validate_model)
        │  sales_tx · sales_monthly · stock_monthly · in_transit · moq · sku_ref
        ▼
app/engine/                    ⏳ фаза 2 — расчёт рекомендаций
app/ui/                        ⏳ фаза 3 — интерфейс и выгрузка
```

Адаптеры поставщиков изолируют различия форматов (разные заголовки, число строк шапки, колонки кратности и товара в пути). Всё, что ниже `app/models.py`, работает с одной схемой и не знает, откуда пришли данные.

## 8. Как проверить решение

Сейчас можно проверить загрузку данных.

**1. Тесты:**

```bash
pytest
```

Ожидаемый результат — `6 passed`.

**2. Загрузка реальных данных партнёра** (~20 секунд):

```bash
python -c "
from pathlib import Path
from app.loaders import load_all
for name, table in load_all(Path('data/raw')).items():
    print(f'{name:14} {table.shape}')
"
```

Команда выводит шесть таблиц единой модели с числом строк и колонок, например `sales_tx` около 249 тыс. строк продаж по накладным обоих поставщиков.

## 9. Данные и интеграции

Источник — выгрузки из 1С, переданные партнёром (`data/raw/`). Данных о клиентах в них нет: в продажах только номер накладной, без ID клиента.

| Данные | IEK | Systeme Electric |
|---|---|---|
| Продажи по накладным | `Динамика продаж_2025-2026.xlsx` | `Динамика продаж_Syseme Electric_2025-2026.xlsx` |
| Продажи по месяцам (01.2024–09.2026) | `Ежемесячные продажи…xlsx` | `Ежемесячные продажи…SystemElectric 2024-2026.xlsx` |
| Остатки на начало месяца | `Ежемесячные остатки…ИЭК.xlsx` | `Ежемесячные остатки SystemElectric 2024-2026.xlsx` |
| Товар в пути на 22.09.2026 | `Путь ИЭК 22.09.2026.xlsx` | `Товар в пути_SystemElectric на 22.09.2026.xlsx` |
| Кратность (MOQ) | `MOQ ИЭК.xlsx` | `MOQ SystemElectric.xlsx` |
| Сезонность по компании (в деньгах) | `Сезонность ИЭК.xlsx` | `Сезонность SystemElectric 2024-2026.xlsx` |

Один склад — Алматы. Данные заканчиваются 22.09.2026, поэтому сентябрь 2026 — неполный месяц. Файлы сезонности в деньгах лежат в репозитории, но загрузчиком не читаются.

Внешних интеграций и API нет.

## 10. Ограничения

**Текущей версии:**
- Реализована только загрузка данных. Расчёта рекомендаций, интерфейса и выгрузки пока нет (фазы 2–3).
- В модели пока нет текущего остатка на дату среза, только остатки на начало месяца. Пустые ячейки остатков пока загружаются как пропуски, а не как ноль. Оба пункта исправляются в фазе 2.
- Загрузка всех файлов занимает ~20 секунд.

**Данных и постановки (останутся и после фаз 2–3):**
- ID клиента в данных нет, поэтому разовые крупные заказы определяются по накладной, а не по клиенту.
- Сроков поставки в выгрузках напрямую нет. Для IEK они восстанавливаются из дат в документах «в пути», для Systeme Electric принимаются как допущение.
- Автоматической отправки заказа поставщику нет и не будет: это запрещено условиями кейса. Сервис только рекомендует, решение за менеджером.
